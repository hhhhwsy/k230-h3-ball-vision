# K230 脱机常驻 RTSP 图传说明

适用环境：庐山派 K230-CanMV、CanMV v1.8 系列固件、2.4 GHz Wi-Fi、OBS 手动观看/录制。

代码只负责以下链路：

```text
摄像头 -> K230 H.264 硬编码 -> RTSP -> Wi-Fi -> OBS
```

它不包含 FFmpeg、本地视频保存、自动录像、按键停止或视觉算法。后续传统视觉应单独添加摄像头通道，不应让电脑端 RTSP 参与控制闭环。

## 一、使用前只改这些内容

打开 `k230_rtsp_stream_only_v1_8.py`，先修改：

```python
WIFI_SSID = "你的热点名称"
WIFI_PASSWORD = "你的热点密码"
```

建议：

- 热点必须开启 2.4 GHz；不要使用仅 5 GHz 的热点。
- 名称和密码优先使用英文、数字，避免空格、中文和特殊符号带来的兼容问题。
- 关闭热点的“随机频段自动切换”或“仅在有互联网时保持热点”等节电选项。
- 比赛时最好使用固定电脑热点或独立路由器；先开热点，再给 K230 上电。
- 在 Windows 热点的“已连接设备”中查看 K230 IP。程序串口也会打印完整 RTSP 地址。

默认图传参数无需先改：

| 参数 | 默认值 | 作用 |
|---|---:|---|
| 分辨率 | 1280×720 | 能覆盖整根管道，同时控制无线负载 |
| 帧率 | 30 fps | 兼顾流畅观察和后续视觉采样 |
| H.264 Profile | Baseline | 提高 OBS/播放器兼容性 |
| 码率 | 2000 kbit/s | 固定俯视画面通常足够 |
| GOP | 30 | 每秒一个关键帧，OBS 重连等待较短 |
| VENC 缓冲 | 8 | 吸收短时间处理抖动 |
| DHCP 后等待 | 8 秒 | 确认 Wi-Fi 已稳定再启动 RTSP |

## 二、先联机测试，再设置脱机启动

1. 先把热点打开。
2. 在 CanMV IDE 或 CanMV VS Code 扩展中手动运行脚本。
3. 串口出现 `K230 脱机 RTSP 图传已启动` 和 RTSP 地址后，再打开 OBS。
4. 连续测试至少 30 分钟，期间关闭并重新打开 OBS 2~3 次；K230 不应重启。
5. 测试通过后，把最终脚本上传并保存为开发板上的 `/sdcard/main.py`。
6. 给开发板完全断电，再重新上电；不要点击 IDE 的“运行”，观察它是否自动连接并推流。

脱机启动时，状态灯含义：

- 慢闪：正在等待、连接 Wi-Fi 或恢复图传。
- 常亮：Wi-Fi、摄像头、编码器和 RTSP 均已启动。
- 快闪约 5 秒：检测到媒体资源卡住，即将复位 SoC。
- 不亮：程序未启动、配置错误，或状态灯 GPIO 与板卡不一致；应查看串口。

如果 GPIO20 已被其他硬件使用，把：

```python
ENABLE_STATUS_LED = False
```

## 三、OBS 输入

OBS 中选择：

```text
来源 -> 添加 -> 媒体源
取消“本地文件”
输入：rtsp://K230_IP:8554/ball
输入格式：留空
网络缓冲：先使用 2 MB
```

录制由 OBS 手动控制。推荐录制为 MKV；每一项正式测试开始时点击“开始录制”，结束时点击“停止录制”。停止 OBS 录制或关闭 OBS 不会停止 K230 的 RTSP 服务。

## 四、Wi-Fi 难连接时怎么判断

本版不会因为热点没开或 DHCP 超时而退出：单次等待 25 秒，失败后按 2、4、8、10 秒间隔无限重试；得到 IP 后还会连续观察 8 秒。运行中掉线时，会先释放 RTSP/摄像头/编码器，再重新连接并重建图传。

Wi-Fi稳定后，程序还会执行：

```python
network.set_default_dev("w0")
```

这一步把RTSP和socket的默认网络接口明确指定为Wi-Fi STA。终端必须出现：

```text
默认网络设备已设置： w0
```

如果没有这行，即使电脑能Ping通K230，RTSP的8554端口也可能没有监听在Wi-Fi接口上。

按以下顺序排查：

1. 确认热点确实工作在 2.4 GHz。
2. 确认 SSID、密码完全一致，尤其是大小写。
3. 把热点名称和密码临时改成纯英文数字测试。
4. K230 和热点距离先控制在 1~2 米，排除信号问题。
5. 关闭电脑无线网卡节电、移动热点自动关闭和睡眠。
6. Windows 防火墙若拦截 OBS，可先允许 OBS 在“专用网络”通信。
7. 若能获得 IP 但 OBS 无画面，先在电脑执行 `ping K230_IP`；Ping 不通是网络问题，不是编码参数问题。
8. Ping能通时继续在PowerShell执行 `Test-NetConnection K230_IP -Port 8554`；只有 `TcpTestSucceeded : True` 才说明OBS能够连接RTSP控制端口。
9. 若 RTSP 地址中的 IP 经常改变，可在路由器/热点端给 K230 做 DHCP 地址保留；不要先在 K230 里写死静态 IP。

不要通过频繁复位来解决 Wi-Fi：Wi-Fi 失败不会触发本代码的整机复位，只会继续重连。

## 五、关于“终止程序后摄像头堵塞”

结论：如果脚本作为 `/sdcard/main.py`，每次冷启动只运行一份并长期保持运行，发生摄像头占用的概率会明显降低。最常见的堵塞场景是：

- `main.py` 已在后台运行，又从 IDE 点击运行第二份脚本；
- 在 Sensor/VENC 的底层调用中被强制停止，`finally` 没有完整执行；
- 前一份代码异常退出，没有调用 `sensor.stop()`、`link.destroy()`、`encoder.Stop()` 和 `encoder.Destroy()`；
- 修改脚本后未整机复位，直接连续运行多次媒体程序。

本版正常停止时会完整执行：

```text
停止推流线程
-> sensor.stop()
-> link.destroy()
-> encoder.Stop()
-> encoder.Destroy()
-> 停止/销毁 RTSP
```

如果推流线程 4 秒内仍不退出、媒体清理失败，或启动时明确返回 `already inited` / `device busy` 一类资源占用错误，脱机模式会等待 5 秒后调用 `machine.reset()`。普通 Wi-Fi 失败、密码错误、OBS 未连接不会触发复位。

调试时请遵守：

1. 设备上已有 `/sdcard/main.py` 时，不要直接再点“运行”。
2. 要调试新代码，先停止当前脚本；若刚刚强制停止过媒体程序，先整机复位一次。
3. 若 REPL 已出现摄像头占用，最可靠的恢复方式是完整断电 3 秒后重新上电。
4. 正式比赛时让 `main.py` 上电自动运行，不在测试项目之间停止图传；OBS 只负责选择是否观看和录像。

## 六、参数怎么调

优先保持 720p30。如果现场 Wi-Fi 抖动，按以下顺序降低压力，每改一次至少测试 20 分钟：

1. 码率从 `2000` 降为 `1600` kbit/s。
2. 帧率从 `30` 降为 `25` fps，同时把 `VIDEO_GOP` 改为 `25`。
3. 最后才把分辨率改为 640×480；此时 `VIDEO_WIDTH=640`、`VIDEO_HEIGHT=480`。

如果画面清晰但钢球有拖影，可在光照固定后尝试：

```python
MANUAL_EXPOSURE_US = 8000
```

然后根据亮度在约 4000~12000 us 内调整。曝光越短，拖影越小，但需要更强、更均匀的补光。

如果画面方向相反，调整：

```python
H_MIRROR = True   # 左右镜像
V_FLIP = True     # 上下翻转
```

## 七、比赛前验收

- 冷启动 5 次，每次都能自行连接并在状态灯常亮后由 OBS 打开。
- 先不开热点给 K230 上电，等待 1 分钟后再开热点，K230 最终能自行连上。
- 图传连续运行 1 小时，实测输出接近 30 fps，无持续花屏。
- 运行中关闭热点 30 秒再打开，图传能自动恢复。
- OBS 关闭再打开 3 次，K230 不需要重启。
- OBS 分别录制、停止 3 次，生成的 MKV 都能回放。
- 正式部署后不再从 IDE 启动第二份媒体脚本。
