# K230 H3 视觉 + RTSP 融合版试运行说明

## 1. 这个版本做了什么

- 只创建并复位一次 `Sensor`。
- CH0：`1280×720 / 30 fps / YUV420SP`，连接硬件 H.264 编码器并通过 RTSP 发给 OBS。
- CH1：`640×480 / RGB888`，运行原有钢球识别并通过 UART2 向 MSPM0 发送数据。
- K230 不保存视频；OBS 负责手动开始和停止录制。
- Wi-Fi、RTSP 和编码流排空在后台运行，视觉和 UART 在主线程运行。
- 未开热点、Wi-Fi 密码错误、OBS 未打开或 Wi-Fi 中途断开时，视觉和 UART 仍继续运行。

融合文件：`k230_H3_ball_rtsp_integrated_v1_8.py`

原来的视觉程序和独立图传程序均未覆盖。

## 2. 第一次运行前必须修改

打开融合代码，在顶部填写现场 2.4 GHz 热点信息：

```python
WIFI_SSID = "你的热点名称"
WIFI_PASSWORD = "你的热点密码"
```

建议热点设置：

- 只用 2.4 GHz，不使用 5 GHz。
- 名称和密码先使用纯英文、数字，避免兼容性问题。
- 关闭“连接设备达到上限”等限制。
- 电脑和 K230 必须连接同一个热点/局域网。
- 尽量固定热点名称、密码和频段，不临时更改。

未填写 Wi-Fi 也能启动视觉和 UART，但不会有 RTSP 地址。

## 3. 第一次联调顺序

1. 先不要命名为 `/sdcard/main.py`，在 CanMV IDE 中手动运行融合文件。
2. 观察实体屏是否有 640×480 视觉画面和 ROI 框。
3. 查看终端是否持续打印 `视觉状态` 和 UART 数据包。
4. 等热点连接成功，再等待程序要求的连续 8 秒稳定时间。
5. 终端出现 `RTSP地址` 后，在 OBS 的“媒体源”中输入该完整地址，例如：

   ```text
   rtsp://192.168.190.53:8554/ball
   ```

6. OBS 中不要勾选“本地文件”，“输入格式”先留空；黑屏时关闭并重新打开该媒体源。
7. 先连续运行 15 分钟，再测试 1 小时。

## 4. 必须重新检查视觉标定

融合后 Sensor 输入模式从原视觉程序的 `1280×960@60` 改为统一的
`1920×1080@30`，CH1 再中心裁剪为 640×480。分辨率仍是 640×480，
但视野范围可能变化，所以原 ROI 和三个位置标定点不能直接认为一定正确。

按实体屏实际画面重新检查这些参数：

```python
ROI_X = 80
ROI_Y = 270
ROI_W = 550
ROI_H = 55
GROOVE_CENTER_Y = 297

PIXEL_AT_NEG_50MM = 220
PIXEL_AT_ZERO_MM = 320
PIXEL_AT_POS_50MM = 420
```

调整原则：

- ROI 只包住凹槽，不能包含大面积车体。
- 把球依次放到 `-5 cm、O、+5 cm`，读取 `RAW_X` 后填写三个像素值。
- 球在屏幕中的直径明显不是约 20～30 像素时，再调整尺寸、面积阈值。
- 先确认单独视觉识别稳定，再评价融合后的帧率。

“先裁 ROI、再转灰度”只减少计算量，不改变 ROI 内的灰度计算结果，不会降低小球识别精度。

## 5. 脱机运行方法

手动联调全部通过后：

1. 把融合文件复制到 K230 SD 卡根目录。
2. 重命名为 `/sdcard/main.py`。
3. 关闭 CanMV IDE 的自动运行/串口占用后，给 K230 彻底断电再上电。
4. K230 会从 `if __name__ == "__main__"` 入口自行启动，不依赖电脑和 IDE。

脱机必须做四项测试：

1. **热点关闭开机**：实体屏识别和 UART 应先正常运行，程序不得卡在 Wi-Fi。
2. **稍后打开热点**：后台应自动连接，稳定 8 秒后给出 RTSP 地址。
3. **运行时关闭热点**：视觉和 UART 应继续；再次开热点后 RTSP 应自动恢复。
4. **OBS关闭再打开**：K230 不应重启，重新连接相同 RTSP 地址即可恢复画面。

如果热点通过 DHCP 分配的 IP 改变，OBS 中的地址也必须随之修改。最好在热点端给 K230 固定 DHCP 地址。

## 6. 摄像头堵塞和停止程序

正常按停止键时，程序按以下顺序释放：

1. 通知 Wi-Fi/RTSP 和编码线程退出；
2. 等待后台 `GetStream` 返回并完成 `ReleaseStream`；
3. 停止 Sensor；
4. 解除 Sensor→VENC 绑定；
5. 停止并销毁 VENC；
6. 关闭显示和 UART。

这样可以降低再次运行时出现 `device busy`、`already initialized` 或摄像头无帧的概率。

不过 CanMV IDE 强制中止、拔线或固件原生调用卡死时，Python 的 `finally` 可能没有机会完整执行。遇到这种情况不要连续点击运行，直接给 K230 断电重启。正式运行采用上电后只启动一次的 `/sdcard/main.py`，确实会显著减少重复初始化造成的堵塞风险。

## 7. 首轮稳定后再做的性能调整

第一次测试保留实体屏，确认 ROI 和识别结果。确认稳定后，正式运行前可修改：

```python
ENABLE_LOCAL_DISPLAY = False
DRAW_DEBUG_OVERLAY = False
DISPLAY_TO_IDE = False
```

这样能减少绘图和显示开销，把更多时间留给视觉。不要先提高到 60 fps：当前融合输入和图传统一为 30 fps，UART 是 25 Hz，先保证稳定更重要。

网络不稳时按此顺序调整：

1. 缩短 K230 与热点距离并固定 2.4 GHz 信道；
2. 将 `VIDEO_BIT_RATE_KBPS` 从 2000 降到 1500；
3. 将 `VIDEO_FPS` 和 `SENSOR_MODE_FPS` 一起降到 25（前提是摄像头模式支持）；
4. 最后才考虑降低图传分辨率。

不要改变视觉分辨率和 ROI 来解决 Wi-Fi 问题，两条通道用途独立。

## 8. 当前能确认与不能替代的验证

已完成静态检查：Python 语法可解析、只有一个 Sensor 实例和一次 reset、
CH0/CH1 显式分开、视觉 snapshot 指定 CH1、没有 FFmpeg/本地录像代码，
并保留了脱机入口和统一清理流程。

PC 端不能模拟 K230 的 Sensor、VENC、RTSP、Wi-Fi 驱动，因此最终可行性仍必须按上面的四项脱机测试在庐山派实机验证。首轮测试时请保存完整终端输出；若失败，优先提供从开机第一行到异常行的全部日志。
